GeoGallery – Schmiedebericht

Selbst gehostete, geografisch organisierte Bildverwaltung für eine feste Gruppe mit ~200.000 Bildern (Ziel 1 Mio.) und öffentlicher Galerie.

Ergebnis: gehärtetZiel: Schärfen20.11.2026

Festgelegte Entscheidungen

Nutzer & Sichtbarkeit
  • Feste Gruppe, gemeinsames Archiv
  • Rollen = was man tut; Gruppen = was man sieht
  • public / angemeldet / Gruppen / privat
  • Restriktivste Einstellung gewinnt
  • Veröffentlichen über Album (album.publish), Bilder ausschließbar
Metadaten
  • Nur Originale tragen EXIF/IPTC/XMP
  • Ableitungen leer bis auf Copyright
  • Öffentliche Positivliste: global → Album → Bild
  • GPS pro Album: exakt / vergröbert / aus
  • Originale unveränderlich, Edits nur in DB
Import & Ablage
  • Admin: SCP/SFTP; sonst Web (später Apps)
  • Verschieben in vom Nutzer gelieferte Ordnerstruktur
  • yyyy-mm-dd_hhmmss.ext + Zähler
  • Pfad nach Import fix, Verschieben nur in DB
  • SHA256-Duplikate geparkt
Ort
  • GPS + Reverse-Geocoding = Wahrheit für Karte
  • Ordnerpfad = Herkunft, eigene Navigation
  • Ohne GPS: Ort aus Ordner („ungefähr“)
  • Widerspruch → Prüfliste
Architektur & Betrieb
  • Ein Host, systemd-Units
  • gRPC über UDS + PostgreSQL-Job-Queue
  • 99,5 %, Datensicherheit vor HA
  • RPO 0 (Originale), RTO ≤ 24 h
Performance (1 Mio. Bilder)
  • Karte < 300 ms (Clustering)
  • Raster < 150 ms, Suche < 200 ms p95
  • Import ≥ 10.000 Bilder/h
  • UI bleibt flüssig während Import

Verworfen – und warum

OptionGrund
NATSZusätzliche Infrastruktur; Pipeline-Status gehört transaktional in PostgreSQL
FlatBuffersDritte Serialisierung ohne Mehrwert
99,9 % VerfügbarkeitMit einem Host nicht verlässlich; Datenverlust ist das echte Risiko
50 gleichzeitige UploadsKein realer Lastfall; Durchsatz zählt
Freigabe-LinksÖffentliche Galerie über Alben genügt
Metadaten in AbleitungenGPS, Seriennummern, Personen würden öffentlich
Rückschreiben in OriginaleBricht SHA256, Duplikaterkennung und Backup
Rechte pro Person/BildGruppen + privat reichen für eine feste Gruppe

Schwachstellen, die übrig bleiben

  • Datenquelle fürs Reverse-Geocoding offen; „Region“ ist international uneinheitlich → bmad-deep-recon
  • Zielhardware unbekannt – Import-Durchsatz muss dagegen geprüft werden
  • Datei-Zeitstempel als Fallback unzuverlässig (Kopie/Download setzt ihn neu)
  • Physischer Pfad wird nach GPS-/Ortskorrektur zur reinen Herkunftsangabe
  • Zählervergabe bei parallelen Workern muss atomar sein
  • Offen: wird der Upload-Pfad des Nutzers automatisch zum Album?

Scope

  • V1: Import + Web-Upload, Pipeline, gängige Formate inkl. HEIC, Ortsmodell, Raster/Detail/Karte, Suche/Filter, Passkey + TOTP, Rollen/Gruppen/Sichtbarkeit, öffentliche Galerie, Metadaten-Edit/Bewertung/Tags, Monitoring, Backup/Restore
  • V1.x: Slideshow, PWA, XMP-Sidecar-Export, pHash, RAW
  • Später: Desktop-App, Mobile-App, Zukunftserweiterungen
